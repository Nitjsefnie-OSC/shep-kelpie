# Handover

A runner replaces its own image with the installed build while worker turns run, and `upgrade` drives it. The agent calls themselves are in agents.md.

- A `handover` trigger replaces the runner's image with the installed build via `shep_handover`, keeping pid, children and shepherd channel, so shep sees no stop. The loop acts at its quiet point (between passes, no `git`/`gh`/merge child), and a call whose stdin is still being fed (`adapters::feeding`) or a notice hook running or queued on its own thread (`Runner::notices_running`) or a reply a forwarder is relaying (cut by the exec) holds it. Only worker turns this image started cross (Claude Code, pi, Codex and goose), each as `Adopted` (pid, record path, `harness`, for pi and goose `Kept`, for Codex the `session` id that names its thread record; `FORMAT` is 5, since an image reading 4 would not know the lease totals, as one reading 3 would not know goose as a `harness`; a build reads 4 and 5) plus its ledger line in `Carry`, which also holds the runner's lease totals and what it holds (`AskerCarry`); a PM, labelling, panel, retro, reviewer or already-adopted flight refuses it, and so does a live pi `attach`, which holds a drain too. Before the exec `Processes::seal` stops reaping, so a call ending then is read by the new image, and refuses while one is being read. The new image waits on each pid with `wait_for_child` and finishes the turn as the old would: output, cost, usage line. The probe checks the target reads `Carry`'s `FORMAT`; the `Fitness` gate starts the target once with `KELPIE_HANDOVER_CHECK` set, as a runner that stops after reading its settings (`starts`), so a build that fails there is refused with the old image running, and then refuses a feed or relay that began meanwhile. A build that still fails after the exec ends the carried calls' groups before the runner exits (`end_groups`), and shep restarts it. Any refusal leaves the old image running; the trigger's answer names why, or says `waiting` after 2.5s and the log has a later refusal. Fd 3 needs no carrying: the shepherd passes it without close-on-exec and `SHEP_CHANNEL_FD` stays set. A pi or goose turn's `Kept` has its forwarder socket, model server and lease id, never the key: the new image reopens the forwarder at that path (`Forwarder::reopen`) with its own gateway settings, and `ModelGateway::resume` renews the lease at once and releases it when the call ends, so no second take, eviction or early release; a chat request in the gap before the reopen is refused. The totals cross because the dog acts only on a total above the last it saw from a run, and a handover keeps the pid, which is the run's epoch: an `Asker` that began at 0 would ask below what the dog recorded and go unheard. A handover from a build that carried no totals starts the `Asker` from the dog's saved book for this run (`Asker::from_book`), or at 0 when the book has none. Adopted turns have no idle watch, unreachable retry or login refresh. A goose turn is carried as pi's is, with one more read: the session's token totals are a file in the call's goose root, so the new image counts the call's usage from them, and the worker's fence plugin and config are files there too, so nothing else is in memory. A Codex turn holds no lease and has no forwarder, so it carries nothing else and the new image finishes it as `run` does (thread record, usage). `src/adapters/pi/adopt.rs`, `src/adapters/goose/adopt.rs`, `src/adapters/codex/adopt.rs`, `src/sheep/handover.rs`, `src/runner/flight/carry.rs`, `src/adapters/process/adopt.rs`, #717, #752, #753, #791, #850
- `shep kelpie upgrade` hands each online runner over before it drains or restarts it, and waits for its `status` `build` (stamp of the file it started from, `upgrade::seen`) to match the installed file. A refusal, a build from before `handover` or no new build in `patience.start` (after a `withdraw_handover`) drains and restarts it as before, saying why. The dog is restarted plainly; `--now` skips the handover. `src/upgrade/handover.rs`, #718
