# CI and the merge

Read 2026-09-26 with gh 2.96.

- `gh pr view --json statusCheckRollup` lists two kinds of check: a `CheckRun` (GitHub Actions, with `status` and `conclusion`) and a `StatusContext` (a commit status such as CodeRabbit's, with `state`). shep's checks include `SKIPPED` runs, which count as passing.
- The playground's pull requests carry no checks at all: an empty rollup. GitHub cannot tell that from CI not registered yet, so a project says whether it runs CI with `ci.block` (then `ci`) in its settings. With it on, an empty rollup is pending, never green; with it off, kelpie reads no checks. The playground's settings have `ci = false`, set 2026-09-27.
- Upgrading the playground's runner past #34 crash-looped it on 2026-09-27: its settings file predated `worker.turn_timeout` and the parser required every key. A key added after a project was created now loads with its documented default: `worker.turn_timeout` 60, `worker.allowed_domains` and `worker.build_env` empty. `ci.block` (then `ci`) stays required, since the design log documents no default for it and a wrong guess either hangs a repo with no CI or merges past checks that never registered.
- A check set registers a check at a time, so kelpie reads a verdict from a head's rollup only two minutes after it first saw that head, and merges two minutes after marking a draft ready, which can start a fresh run on the same head. The same two minutes hold a review back before a reviewer reads a head (ADR 0008).
- Reviewers read red heads (shep-pm/shep-kelpie#423). On a project's pull request on 2026-10-10 the worker pushed and CI failed in 1.5 minutes. The local reviewer spent 8 minutes reading that red head and sent 4 findings. The fix turn pushed a head that was red again, and kelpie summoned a review bot on it.
- A conflict is one turn for the worker. Seen live on the playground's rework of #38: the gate raised a `rebase` ruling, the maintainer sent a note, and the worker resolved it in one turn.
- `gh pr view` lags a push. Seen live 2026-09-27 on the playground: two seconds after kelpie pushed a rebase, it still reported the old head. Kelpie now reads the branch on `origin` after each fetch and waits while the forge's head differs.
- A commit pushed by hand after a CodeRabbit round reached the merge ruling unreviewed. Seen live 2026-09-28 on the scratch repo's PR #5: CodeRabbit satisfied at `0119b4d`, `4887ecf` pushed by hand four minutes later, and the merge ruling followed at `4887ecf` two minutes after that. The foreign-change check then compared only labels and the ready state.
- `gh pr merge --delete-branch` also deletes and switches branches in the checkout gh runs from, so kelpie leaves it out and removes the branch with `git push origin --delete`.
- A forge with "delete head branches on merge" set removes the worker's branch itself, so kelpie's `git push origin --delete` can find it gone. Seen 2026-09-29 after merging shep-pm/shep#639: the push was rejected with `cannot lock ref ... unable to resolve reference`, the runner logged `gate-failed` and finished on the retry. The text varies by git version and host, so kelpie does not match it: after a failed delete it asks `git ls-remote` whether the ref is still on `origin`, and a ref that is gone counts as deleted.
- The runner's own `gh` and `git` calls are plain child processes. The worker's settings file, its sandbox and its denylist apply only to `claude` sessions started with it, so they never reach the project manager's merge, rebase or `--force-with-lease` push.
- A merge queue on `main` (shep-pm/shep-kelpie#213). With one on, `gh pr merge --merge --match-head-commit` queues the pull request and exits 0. GitHub tests it on top of the pull requests ahead of it, then merges it or removes it, and it stays `OPEN` the whole time.
  - `gh pr view --json` has no queue field, so kelpie asks GraphQL for `isInMergeQueue` and the `RemovedFromMergeQueueEvent` timeline items, whose `reason` is free text.
  - Read 2026-09-30 with gh 2.96: with the event filter on, `totalCount` still counts every timeline item (6 on a merged pull request with no removal), so kelpie counts the returned nodes.
- A queued pull request is waited on. Its work item records how many removals it had when kelpie queued it, and skips every gate while the queue holds it, since `main` moves under it. A pull request open and out of the queue with more removals on record went unmerged, and one with none on record gets two minutes' grace before it counts the same. Either goes back to the worker like red CI, with the forge's reason in the prompt, and a second one at the same head raises a `stuck` ruling for `merge-refused`.
  - The workflows run `on: merge_group` so every required check reports in the queue. Turning the queue on is the maintainer's step, and `main` had no ruleset or branch protection when it was written, so "Require merge queue" alone would merge with nothing to wait for.
  - The ruleset on `main` needs: Require merge queue with the merge method Merge commit, and Require status checks to pass with `lint`, `test`, `docs`, `msrv`, `private-names`, `real-shepherd` and `file-size / file-size`. cubic and CodeRabbit never report on `merge_group`, so they stay out of the required checks.
- With a queue required, `gh pr merge` arms auto-merge instead when the pull request cannot be queued yet, and auto-merge queues whatever head the branch has later. Kelpie reads `autoMergeRequest` with the queue and waits on an armed one as it does on a queued one, unless the head moved or CI on it went red: then it runs `gh pr merge --disable-auto` and the work item goes back to CI.
- A work item with a pull request in the queue saves `merge_queued`, which a runner from before this change refuses to load. The state file is one-way while a pull request is queued: roll a runner back only once none is.
- `gh workflow list --repo <repo> --all --limit 1000 --json name,path,state` lists every workflow of a repo with its `state`, the field GitHub documents on "List repository workflows" (`active`, `deleted`, `disabled_manually`, `disabled_inactivity`, `disabled_fork`). Recorded 2026-10-13 with gh 2.96 on shep-pm/shep as `fixtures/gh-workflow-list.json`: 11 workflows, all `active`, two of them GitHub's own dynamic ones (`Dependabot Updates`, `Dependency Graph`, with a `dynamic/dependabot/...` path). A name here is the `workflowName` its runs carry. Not measured: how the list shows a deleted or disabled workflow, since no repo of the maintainer's has one, so the other four states are read from GitHub's docs and tested against a hand-written list. The sandbox's guard hook blocks `gh api` but allows `gh workflow list`.
- A failed run's log tail names its failing tests in three shapes, and counts them in a fourth. Recorded 2026-10-17 with gh 2.96 on four failed runs of shep-pm/shep-kelpie, each kept as `failure_tail` hands it (at most the last 6000 bytes): run 38854765050 in `fixtures/gh-run-log-handover.txt`, run 38807299334 in `gh-run-log-partial-module.txt`, run 38967162070 in `gh-run-log-unlisted-test.txt`, run 38983239961 in `gh-run-log-integration-test.txt`, run 38950550504 in `gh-run-log-no-test.txt`.
  - `test <name> ... FAILED` as each test ends, `---- <name> stdout ----` for each one whose output cargo printed, and the indented list after the `failures:` heading cargo ends a failing run with. `test result: FAILED. <n> passed; <m> failed` counts them.
  - A tail holds several cargo runs, not one. Run 38983239961's tail holds seven: a `     Running tests/<name>.rs (target/debug/deps/...)` header and a `test result` line for each integration test binary, the failing one last. The header names the target before the run, and `error: test failed, to rerun pass `--lib``, or the same with `--test <binary>`, names it after the run's count line. A name belongs to the run it appeared in, which is why kelpie reads both.
  - A tail holds what it has room for. Run 38807299334 named 2 of its 2 failures, but only as its blocks and its final list: the tests failed early in a 4629-test run, so their `test <name> ... FAILED` lines fell outside the 6000 bytes. A run with more failures than the tail holds keeps its count line and loses names, which is how kelpie tells a cut log from a whole one.
  - `gh run view --log-failed` writes cargo's colour marks as the literal text `^[[1m`, `^[[92m`, `^[[91m` and `^[[0m`, not escape bytes, so `strip_colour` in `src/adapters/gh/runs.rs` matches none of them. They wrap cargo's own status words, `Running` and `error` among them, so a parser that matches those words has to take them off first. Each line also carries the job and the step before two tabs, which is why the parser drops the first two fields of every line.
  - Two fixtures carry a home folder path written as `/home/me`, since `scripts/check-private.sh` refuses a home folder path other than `/Users/me` or `/home/me` in any tracked file: `gh-run-log-no-test.txt`, and `gh-run-log-handover.txt`, whose second failed job is the private-names check naming a path in a test. Both paths are GitHub runner folders, not a person's. Nothing else in the five fixtures is changed.
- A fork's first workflow runs wait for a maintainer. GitHub's REST docs ("List workflow runs for a repository") give `status=action_required` for them and `head_sha` as a filter, and "Approve a workflow run for a fork pull request" is `POST /repos/{owner}/{repo}/actions/runs/{run_id}/approve`. GitHub's `status` filter matches a run's status or its conclusion, so kelpie accepts `action_required` in either field. Not measured yet: which of the two a held fork run carries. `fixtures/gh-api-action-required-runs.json` is hand-written in the shape of the docs' example. shep-pm/shep-kelpie#636 records the real listing and finds whether the App's token can approve. Kelpie approves as the maintainer's `gh` login until then.
