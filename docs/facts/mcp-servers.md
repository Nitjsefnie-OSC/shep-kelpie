# MCP servers in a call's transcript

What Claude Code and pi write down of a call's MCP servers, which `kelpie_mcp_servers_total` and `kelpie_mcp_tool_calls_total` are read from (#922, #970). `src/mcp_use.rs`

## Claude Code (2.1.300 and 2.1.301, 2026-10-15)

- `--output-format json` has no init line, so the transcript is the only place a headless call's servers show. It writes how they stand in an `attachment` line of type `deferred_tools_delta`, whose `failedMcpServers` is a list of `{name, errorCode, error}` and whose `pendingMcpServers` and `needsAuthMcpServers` are lists of names.
- The line is written at a session's first call, and again only when the servers stand differently. A resumed call whose server still failed wrote none (measured on 2.1.301, with a server whose command is not there), so the last such line in the whole transcript is how they stood at the end of the call. A later line with an empty `failedMcpServers` ends a failure.
- A session whose servers all connect, with tools not deferred, writes no such line at all (2.1.301, a kelpie reviewer given only the code graph on 2026-10-16). Its `prompt_snapshot` attachment lists the tools sent to the model, each server's with a `server` field naming it, and a failed server's tools are not there. So a call whose servers all connected counted none of them, and `kelpie_mcp_servers_total` could read only `failed`. `fixtures/claude-transcript-mcp-connected.jsonl`.
- A tool call is a `tool_use` block named `mcp__<server>__<tool>`, the server's name with every character but letters, digits, `_` and `-` as `_` (`claude.ai Gmail` is `claude_ai_Gmail`).
- On the maintainer's machine, 220 worker transcripts hold a failed server: `shadcn` 214 (`CONNECTION_CLOSED`), `supabase` 18, a project's own docs server 14, `codebase-memory-mcp` 8, and a plugin's server 2 (`ENOENT`, its command not found). A transcript can hold more than one.
- No worker transcript on that machine has a `mcp__codebase-memory-mcp__*` tool call. The fixture with one, `fixtures/claude-transcript-mcp-tool-calls.jsonl`, was recorded for #922 in a shep-kelpie worktree, with the code graph and a server whose command is not there.

## pi (1.1.0, 2026-10-15)

- pi's session file records no MCP server that failed to connect. A server whose command is not there (`ENOENT`) shows in `pi mcp list` and nowhere in the session file, so kelpie reads how a pi server stood from its tools: `connected` when the session lists one of them in `toolsAdded`, `failed` with none there (#970).
- A server that connected shows only by its tools: with `exposure: direct`, which kelpie sets, they are in the `toolsAdded` of the session's `system` message. A tool call is a `toolCall` block in an `assistant` message, named `mcp__<server>__<tool>` with every character but letters, digits and `_` as `_` (`mcp__codebase_memory_mcp__list_projects`).
- pi writes `toolsAdded` in a `system` message only where the tool set changed, so a session writes it once, in its first `system` message, when a server's tools load (`declareToolChanges` in pi-agent-core 1.1.0's `dist/agent-loop.js`, and a resumed session restores the tools from that message instead of writing a new one). A resumed call's file holds them from the call that wrote them, so kelpie reads the whole file and not the call's own lines. pi writes `toolsRemoved` too, for a server disabled or one that dropped a tool and re-registered it hidden (`hideTools` and `_isDeclarable` in pi 1.1.0's `dist/extensions/mcp/index.js`), and kelpie does not read it: a server whose tools loaded and were hidden later still counts `connected`.
- Kelpie's pi calls on the maintainer's machine wrote 156 session files, 61 of them shep's. Five shep calls were given the code graph before #948: none had its tools in `toolsAdded` and none called it.
- No pi session kelpie wrote has an MCP tool call, so `fixtures/pi-session-mcp.jsonl` was recorded for #922 from pi 1.1.0 against a stand-in model that called the code graph's `list_projects`, with the server connected. Its lines hold no `system` message of its tools, so kelpie counts the server it was given `failed`.
- Why no call had the code graph's tools, on any harness, before #948: the server checks every folder above its index and runtime folder, which sit under the shepherd's home, and every call's sandbox denies reading that (`codebase-memory-mcp.md`). It exited before it connected, which Claude Code records as `CONNECTION_CLOSED` and pi does not record at all. From 2026-10-13 to 10-16, `kelpie_mcp_servers_total` read only `failed`, 49 overnight for two projects.
- pi connects its servers in the background and the first prompt waits only 10 seconds for those with `direct` tools (`DEFAULT_STARTUP_WAIT_MS` in pi 1.1.0's `extensions/mcp/index.js`). A server that connects later has its tools available later, so a cold daemon start slower than that would leave them out of the first request.
- After #949 (2026-10-16, pi 1.1.0, workers on a local model): all 12 pi worker sessions on shep and shep-kelpie had the graph's 17 tools in `toolsAdded`, so the daemon connected inside the sandbox within the 10-second wait. Its logs show 45 starts and no error. The sessions made 2408 tool calls, and none was to the graph. The 17 tools' schemas are 17122 characters, about 4300 tokens, sent with every request. `fixtures/pi-session-mcp-connected.jsonl` is one of those sessions up to its system message, each tool cut to its name and the start of its description.
- `kelpie_mcp_servers_total` counted only Claude Code calls before #970, so it showed none of this. After #949 it read 11 `failed` for shep, all from before 00:30 that day, and no Claude Code call on shep has been given the graph since. A pi call now counts each server it was given, `connected` where its session lists the server's tools and `failed` where it lists none of them, and pi records no reason for the failure, so the standing warning says the tools never loaded.
