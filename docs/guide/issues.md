# Writing issues

The issue writer turns a request into issues an agent can build from. It reads the repo, scopes the request to one pull request's worth, or splits it into the smallest pieces that each work, test and ship on its own, writes acceptance criteria into every issue, and labels each `agent:<name>` with one of the project's implementers.

```sh
shep kelpie issue "let a project be paused from lookout"
shep kelpie issue --interactive "let a project be paused from lookout"
```

On its own, it runs one fresh session in a detached checkout of `main`, files what it writes as `ready-for-human`, and ends with the list of what it filed. shep-kelpie reads each issue back and prints it, with its `agent:` label and the issue it is a sub-issue of. Read them, then label them `ready-for-agent`. An issue without acceptance criteria, its status label or exactly one `agent:` label naming an agent kelpie has a file for with `role: implementer` is named with what it lacks, and the command exits non-zero. A session that fails, or ends without the list, keeps its checkout and prints the `claude --resume` line that picks it up.

On its own there is no one to grill, so a decision the repo's docs and code do not settle is left open, not guessed. The issue it files ends with an `## Open questions` section: each decision as a numbered `❓ **Q1** - **<title>**: ...` question in the format of the `grilling` skill, with a `➡️` recommended answer, so you can answer on the issue before you label it `ready-for-agent`. An issue with nothing left open has no such section.

With `--interactive` it runs `claude` in your terminal, with the issue writer's prompt appended, and the first message `/mattpocock:grill-with-docs <request>`. The `grill-with-docs` skill (`grilling` with `domain-modeling`) interviews you on the request in rounds, each question with a recommended answer, until nothing is left silently assumed. It files nothing until you confirm you share an understanding, and then files what you agree as `ready-for-agent`, onto the board. Before filing it shows the `agent:` label it would put on each issue, and asks whether to apply them, none, or some; an issue with none goes to the default implementer. It is your session, not a runner's: shep-kelpie starts it, and Claude Code asks you before each command it runs and each file it writes.

The session runs in a checkout of a docs branch, `kelpie/docs-<id>`, cut from a fresh `origin/main`, not in your own checkout. As decisions settle, `domain-modeling` writes terms to `GLOSSARY.md` and ADRs to `docs/adr/` there, and its file tools refuse any other file. When the session ends, shep-kelpie commits what it wrote, pushes the branch, opens a draft pull request beside the issues and comments on each issue the session filed with a link to it. A session that wrote no docs leaves no branch. One that somehow changed another file commits nothing and keeps its checkout, which the command names.

In both modes the facts of a request come from the repo, never from you: where a skill would send a sub-agent to look something up, the writer, which has none, reads the repo with its own Read, Grep and Glob. It asks you only for decisions.

Either way the session reads the checkout with Read, Grep and Glob, and nothing outside it: not gh's config, Claude Code's own files or your shell history. On its own it edits no file, and interactively it edits only those two docs paths. Its Bash runs only what `kelpie guard` lists for it: `gh issue create`, `gh issue view <n>` and `gh issue list` on this repo, and, for the issues it filed in this session, `gh issue edit` on labels and `gh api` on their ids and sub-issue and blocked-by links, each as plain words, with a body given as a heredoc behind a quoted delimiter (`--body-file - <<'EOF'`). It runs no git. A hook after each command records the issues it filed and the ids it read, and the guard refuses an edit or a link on any other. The guard also refuses an issue without acceptance criteria, without the status label, or without exactly one listed `agent:` label, and one whose title or body names a path on this machine. On its own the session also runs in the sandbox, with nothing to write but its own scratch folder and only GitHub to reach. Each implementer's `agent:` label is made on the repo the first time the issue writer needs it.

The paths an issue names are checked against `main`. Each path in backticks, whole or by its last parts (`board.rs` matches `src/board.rs`), is resolved against the files of the checkout the writer reads. When a `gh issue create` or `ticket new` names paths that match no file, the guard refuses it once with "these name no file on main" and the paths, and the writer corrects a path that moved or keeps one the issue adds. Filed again, the same paths pass. A path is sent back once per session, and a session with no ledger is not checked. When the board opens an issue, the worker's first prompt names the paths its body names that `main` lacks as "may have moved, or be new", each with the file on `main` that ends the same way when there is one. A path that resolves adds no note. An issue that scopes "every X" lists the Xs.

The issue writer is the agent file `agents.issue_writer` names, `issue-writer` when it names none: edit its body to change its prompt, or its `model` and `effort`, or name a file of your own whose role is `issue-writer`.

The runner asks it too. When the board would open a `ready-for-agent` issue with no `agent:` label and the project lists more than one implementer, one issue writer call reads the issue and the repo, with read tools only, and names the implementer that should build it. `agents.implementer_choice = "order"` skips the call: the issue opens on the first implementer listed, and no label is written on it. shep-kelpie puts that `agent:` label on the issue, and the board opens it on its next poll. The call only picks: it files and labels nothing itself, whatever the agent file says of filing. Its reply's last line of JSON names the agent. It waits on Claude's window like any new work item, even when every role the project lists is local, and `add` refuses the issue while the call runs. The call's line goes in the usage ledger with the issue's number. A call stopped with the runner raises nothing, and the next run asks again. A call that fails, or names no listed implementer, raises a `stuck` ruling on the issue instead of guessing: the board passes the issue over, listed under `skipped` as `unlabelled`, until you answer it. Label the issue, then answer `yes`; an issue still unlabelled goes to the issue writer again. A `no` is refused, since there is no worker to take its note. A label you put on while the call runs stands, and the issue writer's pick goes unused. One labelled while the ruling waits opens anyway, and that clears the ruling. With one implementer listed there is nothing to pick, and an unlabelled issue runs on it.
