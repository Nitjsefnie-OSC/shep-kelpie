# Skills

The skill each step runs, the plugins the repo turns on, and how each harness loads them.

- Every step runs a skill: mattpocock/skills vendored + pinned in `skills/`, kelpie prompts as fallback; `[skills]` overrides a step. A worker's copy holds only the skills its steps run and what those call, from `vendored::CALLS` (closed transitively): a step left out seeds its default only for the worker's four, a step the project names `kelpie` seeds its own (how a named `retro` gets its skill and `writing-for-agents`), and `none`, a `path` and a `plugin` seed nothing, so `triage`, `spec` and `reset` run kelpie's own prompt and name no skill in `status` until the project names one (seeding `triage` would also write the `grilling` and `domain-modeling` it calls, which a harness lists). The cut is what a harness lists: Claude Code names every skill a plugin holds on every request. `write_vendored`, which the interactive issue writer uses, still writes all of them. #147, #993, `crates/core/src/skills/mod.rs`, `crates/core/src/skills/vendored.rs`
- Skills byte-identical; kelpie headless rules win (decide and record, no sub-agents, kelpie reply format, no own `/code-review`). Skill that can't load runs kelpie prompt, logged (unknown slash command passes as text). #170, #147
- A worker's turn carries the headless rules once, in its instructions, so the `implement` and `ci_fix` prompts carry only the slash command and kelpie's reply format beside them; a worker with no `tests`, `pr` or wording skill has nothing in its instructions, and its prompt keeps the block. Retro, triage, spec and reset are calls of their own, and keep it. #992, `crates/core/src/skills/mod.rs`
- Plugins enabled in `.claude/settings.json` on `origin/main` reach every Claude Code agent (skills, agents, commands, hooks, MCP), and a pi, Codex or goose agent's skills and MCP servers (a Codex server as a `-c mcp_servers.<name>` override, one it cannot load dropped with a note, `crates/adapters/src/adapters/codex/mcp.rs`; a goose server as a `--with-extension` or `--with-streamable-http-extension` flag of a new session, none on a resume, so a server added later is not seen, one it cannot load dropped with a note, its tools let through the fence hook by `<key>__`, `crates/adapters/src/adapters/goose/mcp.rs`), never from a worker branch. Sources: plain git transports, no `-` or `::` addresses, no links or `..` (default branch settings aren't maintainer's alone). #569, #570
- The repo's own `.claude/skills`, `agents`, `commands` and the `hooks` of `.claude/settings.json`, read from `origin/main`, are one more plugin, `kelpie-repo`, for every call; a Claude Code call in a worktree whose agent files equal `main`'s (`fence::matches_main`) loads them there and skips it. `repo_setup.own = false` leaves it out. #591, `crates/core/src/skills/repo/own.rs`
- The worker writes its own pull request body, with kelpie's `wording` skill beside the `pr` skill: `mix-v2` of `docs/specs/wording-results.md` cut to "Lead with what they need", "Keep it short" and "Patterns that read as a bot" (the contributor-facing "Sound like a person", "Thanks and praise" and "Humour" dropped), with its `humanizer` and `i-have-adhd` MIT notices, in `skills/kelpie/wording/` beside the vendored copy, which stays byte-identical. It is written to `kelpie-wording` beside `mattpocock` and reaches a call as any plugin does (Claude Code `--plugin-dir`, pi `--skill`, Codex and goose by their linked skill folders). The instructions name it, `/kelpie-wording:wording`, only where they tell the worker to write `pull-request.md`, so it loads when the body is written; a body the worker opens itself is not worded by it. `[skills] pr = none` turns it off with the `pr` skill, and a `pr` replacement keeps it; `[skills]` has no key for a skill outside a step, so it has no switch of its own. Why a skill in the worker and not a representative call: loading it when the body is first written adds 142k units ($0.24) over 10 merged work items, 0.6% of what the workers spent, while a representative call each time the body changes (2 to 4 turns an item) adds 640k units ($2.56), 2.8% (`docs/facts/the-representative-wording-test.md`). #637, #878, `crates/core/src/skills/wording.rs`
- A pi call loads the `skills/` folder of every plugin it is given, the step skill's own folder first so its name wins a collision, after `--no-skills` (nothing of `~/.pi`, `~/.agents` or the worktree loads) and with `--no-approve`. A pi worktree's `.claude` is never read, so the `kelpie-repo` plugin reaches a pi call even in a worktree that matches `main`. A call with no tools gets only its step skill; every other keeps `read`, the way to a skill that names another. Plugin commands, agents and hooks do not reach pi. #763, `crates/adapters/src/adapters/skills.rs`
- A Codex `Tools::Work` call gets every skill folder of every plugin it is given linked into `<call's CODEX_HOME>/skills/<name>` by `prepare`, the first plugin winning a name and the last call's links removed. The call cannot write that folder, so it cannot plant a skill; `~/.agents` stays unread, and `plugins` and `skill_mcp_dependency_install` stay off. A call with no shell cannot open a `SKILL.md`, so it keeps its step skill pasted into the prompt and gets no links. Not measured live (`docs/facts/codex-as-an-agent.md`). #772, `crates/adapters/src/adapters/codex/skills.rs`
- A goose call gets `--with-builtin skills` and a skills folder of its own, `<GOOSE_PATH_ROOT>/config/skills`, which `prepare` empties and rebuilds on every call: a link to each skill folder of every plugin the call is given, named by the `name` line of its `SKILL.md`, the step skill first, then the plugins in order, the first of a name winning (folders inside one plugin go by name). A skill with no `name`, or a `/` in it, is not linked. goose's two builtin skills, `web-search` and `goose-doc-guide`, are shadowed by a stub each that says it is not available, so no worker spends turns on `uvx` or docs it cannot fetch (delete the stubs to bring them back). `~/.agents/skills`, `~/.claude/skills` and `~/.config/agents/skills` are unreadable to the call and its own skills folder unwritable; the worktree's committed skill folders load as on Claude Code, and `.claude`, `.agents` and `.goose` are write-fenced. The step's prompt is goose's command `/<name> <rest>`, so goose injects the skill, unless the skill's text holds `$ARGUMENTS` or `$` and a number, where goose would split `<rest>` like a shell and end the turn on an unbalanced quote: then the prompt stays as written and the model uses `load_skill`, which the fence hook lets through for every kind. A call in `GOOSE_MODE=chat` (no shell, no MCP server) cannot call `load_skill`, so its prompt is the skill's text with the placeholders filled in, and `ARGUMENTS: <rest>`. A skill the worktree's `.agents/skills`, `.goose/skills` or `.claude/skills` holds one of the same name beside is sent as its text too, since goose reads those folders first and the repo's would run in its place. A skill named like a goose command (`help`, `clear` and so on) keeps the prompt as written, since goose would run the command instead. Not run on a model (`docs/facts/goose-as-an-agent.md`). #793, `crates/adapters/src/adapters/goose/skills.rs`
- A plugin's MCP servers and `.mcp.json` on `origin/main` join the call's `--mcp-config` and `permissions.allow` per `parts` and `roles`; not `Retro` calls. #573, `crates/adapters/src/adapters/claude/mcp.rs`
- `[app.dogs.kelpie.repo_setup]` narrows them: `plugins = false` drops the repo's, `roles` picks the calls that get any, `skip` drops `name@marketplace` ids, `parts` picks which of a plugin's parts load (a plugin's hooks stay in its own `hooks/hooks.json`, so they cannot replace kelpie's), `extra` adds ids with a one-string source (`github:o/n#ref`, `git:url`, `directory:dir`) that lookout can edit. The CLI's headless issue writer isn't the runner, so it loads them itself into a per-run folder. #571
