# Contributions

A pull request from someone else is a contribution. The runner sees one before it does anything with it. It lists it, and reads each new head for security before anything of the contributor's runs. It posts nothing and runs nothing for a contribution.

- A contribution is open, not a draft, and not opened by the maintainer (`git.maintainer`, else the login `gh` acts as), by the account kelpie acts as, or by a bot. Logins compare ignoring case. The author decides, never the branch: a fork's branch named `kelpie/5` is still a contribution
- `contributions.pick` sets which ones. `"label"` takes those labelled `ready-for-agent`, `"all"` every one, and `"off"`, the default, none
- Once a minute, whether or not a slot is free, the runner records each contribution with its author and head, and drops the record of one that is closed, merged, a draft again, or, under `"label"`, no longer labelled. A new head updates the record. `status` lists them under `contributions`, and the plain `status` prints a line each
- A quiet clock runs while kelpie waits on the contributor for the current head: from the poll that finds the head's findings recorded, a review bot's threads open (nits included) or CI red. The contributor's comment or review reply written after it began, or a push, starts it over, and a push also clears it until the new head's own results start it again. A reaction and the maintainer's comment do not touch it. A head with green CI, no findings and no open bot thread clears it, since kelpie then waits on the maintainer. `contributions.nudge_days` and `quiet_days` set when it is due: `status` shows each contribution's `waiting_since` and a `clock` with `waiting_for` (seconds), `days_to_nudge`, `days_to_quiet` and `due` (`nudge` or `quiet`), and the plain `status` a line under it. Nothing acts on `due` yet, and red CI before a release gets no comment
- Under `pick = "label"` or `"all"`, `ready-for-agent` on another person's pull request, a draft included, does not adopt it, so a fork's pull request is not refused as one. Under `"off"` it is refused as before. A rework request on a fork's pull request is still refused
- A contributor's code does not run on your machine until something has read it. Each new head gets a security review: kelpie fetches `refs/pull/<n>/head` into the project's checkout (objects only, nothing is checked out) and reads the change since the last head that passed, or the whole change from `origin/main` for a first head or after a force push. `contributions.security_reviewer` (`security-reviewer`, which flags build scripts, workflows, install hooks, network calls, anything near secrets, obfuscated code and text aimed at agents) reads it in a scratch folder under the project's folder that is removed when the call ends, with read tools only, and the diff in the prompt marked as data and never instructions. Kelpie flags in code, without asking a model, a binary change, a symlink, a submodule change and a diff over 200000 bytes, and never passes them. A clean reply records the head as passed, findings record it as flagged with each file, line and why, and a call that fails or answers in no shape leaves the head unread until the next poll. `status` shows each contribution's `security` and `passed`. A flagged head raises a ruling, `security`, naming each file, line and why. It is never posted on the contributor's pull request and never goes to the panel: it reaches you by the webhook, `status` and `shep kelpie rule`. A yes names the head it trusts, `shep kelpie rule 30 yes <hash>` with 7 or more characters of it, so a late yes meant for an earlier head cannot trust a later one; it counts as passed; a no leaves it unpassed, runs nothing and posts nothing. A new push, or the pull request closing or merging, withdraws the ruling with no post, and a late answer to it is refused as stale. Nothing yet runs a passed head
