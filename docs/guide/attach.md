# Attaching to a worker

`shep kelpie attach <issue>` takes over a work item's worker by hand. The runner holds the work item, so no call starts for it. A call already in flight runs to its end, and `attach` says it is waiting. Then it resumes the worker's session in your terminal (`claude --resume` for a Claude Code worker, `pi --session` for a pi worker), in the item's worktree, with the worker's settings file and inside the worker's sandbox, so its deny rules, its guard and its fence hold while you drive. Claude Code asks before each tool call as it always does. pi asks before none: the sandbox and the worker's guard extension are what hold, as they do for its turns, so a command the worker could not run, you cannot either. A pi session reaches its model through a forwarder kelpie keeps open until the session ends, and it takes no gateway lease.

When you exit `claude`, the work item carries on, and its next turn resumes the same session. A commit or push you make while attached is the worker's own, as a push in a turn is, so the gate takes it as the branch's head rather than a change kelpie did not make. The runner holds the work item while either the `attach` command or the session it started runs, each known by its pid and start time, and lets it go at its next pass once both have ended. A SIGTERM or SIGHUP to `attach` is passed on to the session, which `attach` waits for. `status` shows the hold under the item's `attached`, and `drop` refuses the item while it is held.

`attach` changes nothing and says what to do instead for a work item whose worker has no session yet (its first turn starts one), one parked on a ruling (answer it first), one holding no slot under `concurrency.active_items` when none is free (its session would be one more model call; with one free, `attach` takes it), or one merging. Only a Claude Code or pi worker can be attached: a Codex worker's session resumes another way, by hand. While a pi session is attached, a handover to a new build waits, since the session's forwarder lives in the running build's memory and the new build would not have it. It goes on once the hold is gone.
