# A build folder fills the disk

- On 2026-10-14 the maintainer's Mac ran out of disk (137 MB free of 926 GB) and every tool call failed. One work item caused much of it: shep's #358 needs handover blobs written by older shep versions, so its pi worker checked out 12 old tags and built each into its build folder (`CARGO_TARGET_DIR`). That made 61 copies of `shep-daemon` and 33 GB in 45 minutes, inside one turn. shep's build folders held 55 GB across 7 open items.
- A cargo profile folder (`debug`, `release`, or either under a target triple) holds `.fingerprint/`, `deps/`, `incremental/` and `build/`. The newest binary in `deps/` is hard-linked into the profile folder, so removing its `deps/` link frees nothing until the other link goes too. The stale copies in `deps/` and `incremental/` have no second link.
- On Unix the free space of the disk is `f_bavail * f_frsize` of `statvfs`. A folder's size counts `st_blocks * 512` of each file, once per hard link target, so sparse files and linked artifacts are not over-counted.
- On Windows `GetDiskFreeSpaceExW` reads bytes free to the caller. `GetFileInformationByHandleEx(FileStandardInfo)` reads each file's `AllocationSize` from the same handle that `GetFileInformationByHandle` reads its volume serial, file index and link count from. The walk counts a target with more than one link once per (volume serial, file index). These readings are compiled by the `windows` job's `cargo check`, not run.
