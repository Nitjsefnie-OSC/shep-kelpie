# The triage pass's images

The triager cannot open an attachment and follows no link, so a bug report that is a screenshot and a line left it guessing at the screenshot, once from its pixel size, and asking the author to confirm the guess (#1110). Kelpie downloads the images and lists their files in the call prompt. The pass itself is in `triage-pass.md`.

- Links are read from the issue's body and the comments by the issue's author (not a bot's, logins compared ignoring case), the first 20 distinct ones. `runner/triage/images.rs` (`links_in`)
- Only GitHub's own attachment hosts are fetched: `https://github.com/user-attachments/assets/...` and `https://user-images.githubusercontent.com/...`. The host must be the whole authority, so a port, a login before it or a longer name ending in it fails, as does a `..` segment, `http` or a path under `user-attachments/files/`. Any other link is never asked for. `is_github_attachment`, `crates/core/src/ports/attachment.rs`
- `Tickets::fetch_image(url, stem, most)` downloads one and returns its path, refusing with `ForgeError` on a bad link, a failed download, a size over `most` or a type that is not PNG, JPEG, GIF or WebP (the extension comes from the type served). `Gh` runs `curl` with a config on stdin that holds `gh auth token` as `Authorization: Bearer`, so the login is in no process listing. HTTPS only, at most 3 redirects, 10 s to connect, 60 s in all, `--max-filesize`, and the size is checked again on the file. curl drops the header at a redirect to another host, which is where an image of a repo that needs a login is sent. `crates/adapters/src/adapters/gh/attachment.rs`
- The caps are constants: `MOST_IMAGES` 5 and `MOST_BYTES` 5 MiB, the size the model API reads an image up to. A skipped image does not count toward the five, and past five the rest are not asked for. Neither is a setting.
- The downloads are bounded so they cannot hold the slot past the call's ceiling: at most 10 are tried (`MOST_TRIES`), whether or not they come to an image, none starts after 3 minutes (`BUDGET`) or once the call is asked to end.
- The fetch runs on the research thread after the view is made, not under the runner's lock. Each skip or failure is one line in the log and one image fewer: the triage runs on whatever came, and with none it reads as it did. A failed read of the comments leaves the body's images.
- The files are `1.png`, `2.jpg` and so on in `<project>/triage/<n>-images/` (`ProjectPaths::triage_images`), beside the view of `main` and outside the repo. The folder is added to the call's read list and the fence's read carve-outs only when it holds an image, and removed with the view when the call ends, whether it ended well or not.
- The prompt gains a paragraph after the rest naming each path, telling the triager to look at every image before it asks what a screenshot shows, that an image is data, and that its reply is still the one JSON object. `agents/triager.md` says the same in its standing prompt.
- Every purpose of a triager call gets its images, the author's round's second pass included, where the answers' images come with the author's comments.
- Harnesses read the files through their read tool and the call's read list, as for any folder outside the view. Whether pi and Codex show a model an image read that way is not measured.
