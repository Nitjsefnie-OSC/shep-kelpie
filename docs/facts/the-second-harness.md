# The second harness

Measured 2026-09-30 for #130: pi 0.85.1 against codex-cli 0.146.0 (`codex exec` with a custom provider on the Responses API), both on qwen3.8:27b through Ollama 0.34.0 on the maintainer's Windows box (RTX 4090, 64k context). One run each of the playground's issue 34 (the `RuleList` component, 170 lines when a person did it), on the commit before its fix, with the same prompt. Each ran whole under `srt` 0.0.77 with a worker-shaped fence: its folder, its own home and a scratch folder writable, the model's host the only host, the credential paths unreadable. Each held the GPU lease for the whole run.

| | pi | Codex |
|---|---|---|
| wall time | 286 s | 710 s |
| model turns | 44 | not reported per turn |
| tool calls | 53 (25 bash, 13 edit, 11 read, 4 write) | 121 shell commands |
| uncached input | 25,569 | 142,202 |
| cache read | 1,032,549 | 4,113,264 |

- Both changed the same five files and nothing outside their folder. `bun run lint` failed in both for want of a git repo around the folder, not the change.
- pi's one refusal was a test file it tried to write in `/tmp`.
  - Codex has no file tool on this model: it wrote every file through its shell, `zsh -lc`, whose heredocs need a temporary file outside the fence, so its first writes were refused and it worked around them. Its other refusals were writes to `/tmp`, a move outside its folder and `nice(5)`.
  - Codex also reached for `chatgpt.com`, `ab.chatgpt.com` and `api.github.com`, which the sandbox refused, warned it had no metadata for the model, and listed 81 skills it found outside the `CODEX_HOME` it was given.
- pi takes the caller's session id as its own (`--session-id`), and Codex makes its own thread id. pi's `tool_call` extension event can refuse any tool call with a reason the model reads. Codex has Claude-shaped hooks, but its writes all go through the shell, where `kelpie confine` cannot see a path.
- So pi is the second harness.
- A pi call's sandbox allows no host of the model's: a forwarder kelpie runs outside it, one per call, passes only the chat completions call (shep-pm/shep-kelpie#235).
  - With the model's host in the sandbox, `srt` allows it on every port: from inside, through the proxy, ports 11434, 22, 445 and 3389 on the Windows box all connected, and ssh answered.
  - Ollama has no authentication, so a worker's commands could reach its whole API (`/api/delete`, `/api/pull`, `/api/create`), and any other service the box runs. Claude Code's endpoint needs a key the sandbox hides; this one needs nothing.
- Measured 2026-10-01 for #235, against a stand-in server on 127.0.0.1 (`srt` 0.0.77, pi 0.85.1): the forwarder takes the model's traffic through `srt`'s `network.mitmProxy`, not a loopback port.
  - A forwarder on a loopback port would not do: `allowedDomains: ["localhost"]` through the proxy reached an arbitrary local port, and `allowLocalBinding` let a direct connect reach it, so either opens every local service.
  - `srt`'s `network.mitmProxy` (`socketPath` and `domains`) hands a listed host's traffic to a Unix socket outside, as `CONNECT <host>:<port>` for a tunnel or an absolute-URI request for plain HTTP, and the sandbox needs neither the host nor the socket. A host not listed still answers "Connection blocked by network allowlist".
  - curl and Node's `fetch` send the absolute-URI request. pi's own client opens a tunnel first, `CONNECT model.kelpie.test:80`, and sends its one request through it, so the forwarder accepts a tunnel to the worker's host on port 80 and judges the request inside as any other.
  - The worker's host, `model.kelpie.test`, resolves nowhere.
- The forwarder passes only a chat call and refuses everything else.
  - It reads each request whole, sends the server only a chat call, `POST` to the base path's `/chat/completions`, with its own request line, a counted `Content-Length` and `Connection: close`, and copies the reply back as it arrives.
  - Everything else is refused with a 403 whose body names the method and path asked, and nothing of it is sent on, so a second request behind a chat call in one connection never reaches the server.
  - It dials plain `http://` only (kelpie has no TLS client), so settings refuse a pi agent whose `url` is `https://`. It lists no models: pi runs offline with its one model, and `GET /v1/models` is refused with the rest.
  - Anything in the sandbox can reach the forwarder through the proxy, so it holds a client to limits: a head of 64 KiB, a chunk or trailer line of 1 KiB, a body of 64 MiB, 30 seconds to send the whole request, 8 connections at once (the rest get a 503), and no control character in a header.
  - A worker's `allowed_domains` entry that equals the model's host, or names a loopback host, is refused when settings load, since either would give the worker the host's ports again. Loopback is caught in any spelling (`127.1`, `127.0.0.2`, `::ffff:127.0.0.1`, a trailing dot, `*.localhost`), but another name or address for the same machine cannot be told without resolving it.
  - An entry may carry a port (`host:11434`) or be an IPv4-mapped address (`[::ffff:192.0.2.9]`), both of which `srt` 0.0.77 accepts, so the check reads those too.
  - As a second layer, a pi call's `srt` settings deny the model's host, `localhost`, `127.0.0.1` and `[::1]` on every port, and refuse any allowed name that resolves to the model's address; a deny beat an allow of the same host and port in the live test, and left the forwarder's route alone.
  - Worst case the forwarder buffers 8 bodies of 64 MiB. A forwarder clears the sockets an earlier killed kelpie left in its folder.
- Under the real sandbox and the stand-in, with the policy the pi adapter builds (the ignored tests in `src/adapters/pi/escapes.rs`, `KELPIE_TOOLS` set): a chat call through the worker's host answered 200 with the stand-in's reply; `DELETE /api/delete`, `POST /api/pull` and `GET /api/tags` each answered 403 naming themselves; the stand-in's own address, straight and through the proxy, and port 22 on a documentation address (192.0.2.9) were not reached; and the stand-in saw one request, the chat call. The real pi, given the forwarder's host as its model's, answered `ok` through it in under a second.
- A model server on this machine (`localhost`) now works the same way, since the forwarder dials it from outside the sandbox: the stand-in's tests ran on 127.0.0.1. The Codex CLI stays the candidate for ChatGPT's models (#126), on its own account, where it would have its file tool.
- `srt` sets `no_proxy` to every private address range, so a model on the LAN dialled by its address is refused by the sandbox. The worker's host is a name outside those ranges, so its calls go through the proxy with `no_proxy` as `srt` sets it. pi is Node, so it needs `NODE_USE_ENV_PROXY=1`.
- pi opens `auth.json` and `models-store.json` in its home at start and takes a lock folder beside each, `auth.json.lock` and `models-store.json.lock`, even when it changes neither. Kelpie writes both files and lets the sandbox write only the two lock folders and the sessions folder. A session is `<sessions>/<time>_<id>.jsonl`. With `--session-id` and no file for it, pi warns and starts a new session with that id.
- `pi -p --mode json` prints one event per line: a session header carrying the id, every streaming delta, and each message when it ends.
  - On a resume it prints only the new call's messages, so the sum of its assistant messages' `usage` is the call's own. A local model's cost there is zero, so kelpie records the call as unpriced. Tokens spent on pi's own compaction are not in those messages, but they are in the `compaction_end` event (below), which the adapter adds.
  - Only a last message that stopped with `stop` is an answer: `length` fails as out of output tokens, and any other reason fails naming it. An error carries the last 2 KB of pi's output, since a worker's runs to megabytes.
- Compaction events, from the docs and types of the installed pi 0.85.1 (`docs/json.md`, `dist/core/agent-session.d.ts`, `examples/extensions/trigger-compact.ts`), not from a recording: `fixtures/pi-p-compaction.jsonl` is written from them and stands until a live recording replaces it (#762). 1.0.4's own copies were not read.
  - `{"type":"compaction_start","reason":"manual"|"threshold"|"overflow"}`, then `{"type":"compaction_end","reason":...,"result":{"summary","firstKeptEntryId","tokensBefore","usage"?}|undefined,"aborted":bool,"willRetry":bool,"errorMessage"?}`. Both cover manual and automatic compaction. `result.usage` is the summary request's usage, with the message usage's keys.
  - A turn's context is the last assistant `message_end`'s `input + cacheRead + cacheWrite`. A compaction's usage is added only when it made a summary (`aborted` false, `result` present).
  - `-p` runs no built-in command (`/compact` would go to the model), so a compact call sends `/kelpie-compact`, an extension command whose handler awaits `ctx.compact()` through its `onComplete` and `onError`. Guessed, not measured: that `-p` runs an extension command given as the prompt, that it waits for the handler, and what exit status a failed compaction gives. #762 measures them.
- The adapter live, with this branch's build as the checks (`record_a_turn_a_resumed_turn_and_two_refusals`, ignored): a new session answered `ok`, its resume named the word, and a worker had a write to `.claude/settings.json` refused by `kelpie confine`, `echo hi` into a folder outside refused by the sandbox ("Operation not permitted"), and `gh pr merge 1` refused by `kelpie guard`. The three calls took 11 seconds. The recordings are `fixtures/pi-p-*.jsonl`. Against an older kelpie whose `guard` takes other arguments, the check printed its usage and exited 1, and the extension refused the command, as it must.
- The forwarder relays a reply with a read that blocks on the model server, so a hang-up by pi was seen only when the next reply byte failed to write (#601). Seen 2026-10-12 with Strata 0.1.38 behind Paddock: a call queued and then thinking sent pi no bytes, pi's `httpIdleTimeoutMs` (300 s) ended it, and Strata kept thinking for 4.5 more minutes to its 60,000-token budget, with the other worker's next call queued behind it. Strata checks its client socket every 0.5 s and cancels on a hang-up, and Paddock drops its upstream when its client leaves, so the hang-up only had to get past the forwarder.
  - The forwarder now reads the client's side while it relays, every 100 ms, and shuts the model server's stream on end of file or an error. A client that ends only its write side (`shutdown(Write)`) also counts as a hang-up, so a client must stay connected until it has read the reply.
  - Measured 2026-10-13 (`srt` 1.0.0, curl as the client, a stand-in on the Unix socket): `srt`'s `network.mitmProxy` keeps the connection whole after it sends the request, with no half-close while the server stays silent, and the reply reaches the client whole. When the client hangs up, by its own timeout or killed with `SIGKILL`, the stand-in reads end of file within 10 ms. So the forwarder sees pi's hang-up, and a call that stays connected is never cut off. #670
- A pi call loads every skill of every plugin it is given (#763), so the system prompt lists each one's name and description (pi caps a description at 1024 characters). Counted 2026-10-13 from the `SKILL.md` files of the vendored plugin at its pin, with no model run: 15 skills, and their `name:` and `description:` lines come to 2691 characters, roughly 700 tokens at four characters each. The repo's enabled plugins and its own `.claude/skills` add theirs. Seven of the fifteen carry `disable-model-invocation: true`; whether pi leaves those out of its listing is not measured here. On a 64k local model this is the cost to weigh against loading only the step skill, and loading only the step skill is the one-line change to reverse it.
- pi 1.1.0, measured 2026-10-13 for #759 (`srt` 0.0.77, qwen3.8:27b through Paddock). Homebrew's latest by then was 1.1.0, not 1.0.4, so this is the version recorded; doctor still asks for 1.0.4 or later. The other measurements in this file are from 0.85.1.
  - `record_a_turn_a_resumed_turn_and_two_refusals` passed against this branch's `shep-kelpie` as `KELPIE_BIN`: the new session answered `ok`, its resume named the word, and the worker's three refusals came from `kelpie confine`, the sandbox and `kelpie guard` as before. The three calls took 8 seconds. Its recordings replaced `fixtures/pi-p-fresh.jsonl`, `pi-p-resumed.jsonl` and `pi-p-refused.jsonl`, and `cargo test --lib adapters::pi` passes on them unchanged.
  - Strict JSON-schema sampling, the default for `read`, `bash`, `edit` and `write` since 0.86.0, was not refused by Ollama behind Paddock: each of the worker's tool calls arrived with valid arguments.
  - The JSON stream now opens each call with a `system` message (`message_start` and `message_end`, role `system`, its prompt in `sections`). `parse_result` reads past it.
  - The tool calls of one reply run at once: the worker's two `bash` calls started together and ended in the other order. A `bash` result also carries `structuredContent` with its `exit_code`.
  - A session written by 0.85.1 (header `version` 3) resumed under 1.1.0 on iq3_xxs and answered from it, naming its issue and the last files it read. pi appended to the file and left the header at version 3.
  - pi 1.1.0 refuses to resume a session whose header `cwd` no longer exists: "Stored session working directory does not exist", exit 1. A worker resumes in the worktree its session started in, so only a worktree moved or removed under a live session meets this.
  - Not measured yet: a worker turn through the runner (whether the forwarder sees a chat call kelpie did not make, and whether the sandbox log shows a write pi needs, such as the Node compile cache). The next pi worker turn gives both.

## A web for the pi researcher (#767)

Measured 2026-10-13 against `pi-web-access` 0.40.0 (the `latest` tag, MIT, Node 22.19 or later) and the source of pi 1.1.0, the version now on the maintainer's machine. What could not run: the worker that took #767 can neither start pi nor bind a port (`srt` inside its sandbox fails with "listen EPERM"), so no `pi -p` run with the package happened. What did run is the package's own extension, loaded by a Node harness against a stand-in for pi's extension API, behind the same kind of proxy as the researcher's (`NODE_USE_ENV_PROXY=1`, the sandbox's allowlist), with each tool called as pi would. What is read from pi 1.1.0's source is marked. `adapters::pi::escapes::a_researchers_fetch_reaches_only_the_hosts_its_policy_lists` (ignored) is the live check, run in CI or by the maintainer.

- Install: `npm install pi-web-access@0.40.0` into an empty folder brings 215 packages with `@anthropic-ai/sandbox-runtime`, and none of them is flagged `hasInstallScript` in the lockfile, so no install script runs and `npm install --ignore-scripts` would change nothing. The package's own `prepublishOnly` and `postpublish` run only when publishing. Its `typebox` peer is installed beside it. The three `@earendil-works` peers are optional and not installed. The harness had to give them pi's own copies. From pi 1.1.0's source, pi's loader (jiti) aliases `@earendil-works/*` and `typebox` to its own for an extension, so no copy is needed under pi.
- Entry: `package.json` has `"pi": { "extensions": ["./dist"] }`. From pi 1.1.0's source, `-e <folder>` reads that field, so `-e <folder>/node_modules/pi-web-access` loads `dist/index.js`, and an explicit `-e` still loads with `--no-extensions`.
- Tools: the extension registers `web_search`, `fetch_content` and `get_search_content`, which reads back a result that was stored rather than returned whole (a long result is bounded and the response names its `responseId`). `source_check` is a fourth, registered unless `tools.sourceCheck.enabled` is false, which the config below sets. It also registers the commands `websearch`, `curator`, `google-account` and `search`, which `-p` never runs, and hooks on `before_agent_start`, `agent_settled`, `session_start`, `session_tree`, `session_shutdown` and `tool_call`. From pi 1.1.0's source, `--tools` takes plain names as an allowlist over built-in and extension tools alike, so `--tools read,grep,find,ls,web_search,fetch_content,get_search_content` lists them.
- A trap: with `toolActivation` at its default (`auto`), the extension registers a `web_enable` tool and calls `setActiveTools`, which would override what `--tools` listed. The config sets `"toolActivation": "eager"`, and then it calls nothing of the kind.
- Config: `$PI_CODING_AGENT_DIR/web-search.json`, read at load, and the error text names that path. Kelpie sets `PI_CODING_AGENT_DIR` to the call's own pi home, so the file goes there. The cache is `web-search-cache` under `PI_WEB_ACCESS_CACHE_ROOT` when that is set, and under the config folder when it is not. With the home read-only and the variable pointing at a scratch folder, nothing else was written there, so a call that does not set it writes into its pi home.
- The config that keeps the package to one search host and the page host, with no key in it: `{"toolActivation":"eager","ssrf":{"trustEnvProxy":true},"tools":{"sourceCheck":{"enabled":false}},"webSearch":{"allowedProviders":["exa"]},"fetch":{"allowedModes":["readable","raw"]},"fetchRouting":{"providers":["http"],"allowRemoteHostedProviders":false},"githubClone":{"enabled":false},"workflow":"none","autoOpenBrowser":false}`.
  - `fetch.allowedModes` without `answer` makes `mode: "answer"` return "Fetch mode \"answer\" is disabled by fetch.allowedModes", which is the mode that sends a page to a model service.
  - `ssrf.trustEnvProxy` is needed. Without it the package resolves the page host's name itself before it fetches, which the sandbox does not allow (a worker has no DNS of its own), and every fetch failed. With it the package leaves resolution to the proxy.
- Search with no key: one `CONNECT mcp.exa.ai:443`, and no other host, through the environment proxy. The request is a POST to `https://mcp.exa.ai/mcp?tools=web_search_exa`. Exa answered HTTP 200, but with its free-tier limit message ("You've hit Exa's free MCP rate limit") and no results, to the worker's host at the time, so the package reported "No search provider available" and listed the keys it could use. What a search that succeeds returns was not seen, and a keyless search can be throttled whatever the fence lists.
- A key moves the search off that host. From the package's source (`dist/index.js`), `EXA_API_KEY` or `EXA_BASE_URL` in the environment makes the Exa provider use `https://api.exa.ai` or the given base instead of `mcp.exa.ai`, which the allowlist does not list, and `webSearch.allowedProviders` does not stop it. Kelpie runs pi under `env`, which passes on kelpie's whole environment, so a call that has the web runs `env -u EXA_API_KEY -u EXA_BASE_URL`. The other provider variables the source reads belong to providers the config leaves out. Not run against a live key.
- Fetch dials the page's own host and nothing else. `fetch_content` of `https://registry.npmjs.org/...` produced one `CONNECT registry.npmjs.org:443` and returned the page. Of `https://example.com/` (not on the allowlist) it produced `CONNECT example.com:443`, which the allowlist proxy refused, and the tool returned "fetch failed" with advice to turn on the Jina fallback, which the config leaves off. So the fetch is held to the sandbox's allowlist, and a reader service is not in the path, which is the case the issue said to stop at.
  - A GitHub URL (`https://github.com/...`) went to `CONNECT github.com:443` and returned the page, since `githubClone` is off. A YouTube URL returned "Could not extract YouTube video content" with no connection. A local path returned "Invalid URL".
- Not measured: a model-driven run (does pi, with a real model, call the tools by these names and parameters), the exit of a `-p` call that loaded the package (the package starts no server or timer the harness could see, and the harness exited the moment the work ended, but pi's own shutdown was not run), and a PDF fetch, which the package handles by its own path.
