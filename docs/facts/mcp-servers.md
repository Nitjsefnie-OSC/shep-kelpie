# MCP servers in a call's transcript

What Claude Code and pi write down of a call's MCP servers, which `kelpie_mcp_servers_total` and `kelpie_mcp_tool_calls_total` are read from (#922, #970). `src/mcp_use.rs`

## Claude Code (2.1.300 and 2.1.301, 2026-10-15)

- `--output-format json` has no init line, so the transcript is the only place a headless call's servers show. It writes how they stand in an `attachment` line of type `deferred_tools_delta`, whose `failedMcpServers` is a list of `{name, errorCode, error}` and whose `pendingMcpServers` and `needsAuthMcpServers` are lists of names.
- The line is written at a session's first call, and again only when the servers stand differently. A resumed call whose server still failed wrote none (measured on 2.1.301, with a server whose command is not there), so the last such line in the whole transcript is how they stood at the end of the call. A later line with an empty `failedMcpServers` ends a failure.
- A session whose servers all connect, with tools not deferred, writes no such line at all (2.1.301, a kelpie reviewer given only the code graph on 2026-10-16). Its `prompt_snapshot` attachment lists the tools sent to the model, each server's with a `server` field naming it, and a failed server's tools are not there. So a call whose servers all connected counted none of them, and `kelpie_mcp_servers_total` could read only `failed`. `fixtures/claude-transcript-mcp-connected.jsonl`.
- A tool call is a `tool_use` block named `mcp__<server>__<tool>`, the server's name with every character but letters, digits, `_` and `-` as `_` (`claude.ai Gmail` is `claude_ai_Gmail`).
- On the maintainer's machine, 220 worker transcripts hold a failed server: `shadcn` 214 (`CONNECTION_CLOSED`), `supabase` 18, a project's own docs server 14, `codebase-memory-mcp` 8, and a plugin's server 2 (`ENOENT`, its command not found). A transcript can hold more than one.
- No worker transcript on that machine has a `mcp__codebase-memory-mcp__*` tool call. The fixture with one, `fixtures/claude-transcript-mcp-tool-calls.jsonl`, was recorded for #922 in a shep-kelpie worktree, with the code graph and a server whose command is not there.

## pi (1.1.0, 2026-10-15)

- pi's session file records no MCP server that failed to connect. A server whose command is not there (`ENOENT`) shows in `pi mcp list` and nowhere in the session file, so kelpie reads how a pi server stood from its tools: `connected` when the session leaves one of them available as it ends or answers one of its tool calls, `failed` with neither (#970).
- A server that connected shows only by its tools: with `exposure: direct`, which kelpie sets, they are in the `toolsAdded` of the session's `system` message. A tool call is a `toolCall` block in an `assistant` message, named `mcp__<server>__<tool>` with every character but letters, digits and `_` as `_` (`mcp__codebase_memory_mcp__list_projects`).
- pi writes `toolsAdded` in a `system` message only where the tool set changed, so a session writes it once, in its first `system` message, when a server's tools load (`declareToolChanges` in pi-agent-core 1.1.0's `dist/agent-loop.js`, and a resumed session restores the tools from that message instead of writing a new one). A resumed call's file holds them from the call that wrote them, so kelpie reads the whole file and not the call's own lines.
- pi writes `toolsRemoved` for a server disabled or one that dropped a tool and re-registered it hidden (`hideTools` and `_isDeclarable` in pi 1.1.0's `dist/extensions/mcp/index.js`). Kelpie reads the last word the file says of each server, in the order the file holds them: an addition, or a `toolResult` with `isError` false for one of its tools, leaves it standing, and a removal that left none of its tools does not. Tools added in an earlier call and removed since count `failed`, and one tool of a server left counts it `connected`.
- A `toolResult` with `isError` true is no word for or against a server. pi writes it for a tool whose server failed (`Tool <name> not found`, and every tool error, in pi-agent-core 1.1.0's `dist/agent-loop.js`), which covers a server whose connection closed and a tool the model named wrongly.
- A server that connected and died mid-session leaves no line of its own: pi writes `toolsRemoved` only for tools it re-registers hidden. Kelpie reads such a server as its last answer left it.
- Kelpie's pi calls on the maintainer's machine wrote 156 session files, 61 of them shep's. Five shep calls were given the code graph before #948: none had its tools in `toolsAdded` and none called it.
- No pi session kelpie wrote has an MCP tool call, so `fixtures/pi-session-mcp.jsonl` was recorded for #922 from pi 1.1.0 against a stand-in model that called the code graph's `list_projects`, with the server connected. Its lines hold no `system` message of its tools, and the call comes back with `isError` false, so kelpie reads the graph from that answer.
- Why no call had the code graph's tools, on any harness, before #948: the server checks every folder above its index and runtime folder, which sit under the shepherd's home, and every call's sandbox denies reading that (`codebase-memory-mcp.md`). It exited before it connected, which Claude Code records as `CONNECTION_CLOSED` and pi does not record at all. From 2026-10-13 to 10-16, `kelpie_mcp_servers_total` read only `failed`, 49 overnight for two projects.
- pi connects its servers in the background and the first prompt waits only 10 seconds for those with `direct` tools (`DEFAULT_STARTUP_WAIT_MS` in pi 1.1.0's `extensions/mcp/index.js`). A server that connects later has its tools available later, so a cold daemon start slower than that would leave them out of the first request.
- After #949 (2026-10-16, pi 1.1.0, workers on a local model): all 12 pi worker sessions on shep and shep-kelpie had the graph's 17 tools in `toolsAdded`, so the daemon connected inside the sandbox within the 10-second wait. Its logs show 45 starts and no error. The sessions made 2408 tool calls, and none was to the graph. The 17 tools' schemas are 17122 characters, about 4300 tokens, sent with every request. `fixtures/pi-session-mcp-connected.jsonl` is one of those sessions up to its system message, each tool cut to its name and the start of its description.
- `kelpie_mcp_servers_total` counted only Claude Code calls before #970, so it showed none of this. After #949 it read 11 `failed` for shep, all from before 00:30 that day, and no Claude Code call on shep has been given the graph since. A pi call now counts each server it was given, `connected` where its session leaves the server's tools available as it ends or answers one of its calls and `failed` where it does neither, and pi records no reason for the failure, so the standing warning says the tools were not in the session as the call ended.

## What a call given the code graph pays for it (Claude Code 2.1.300 to 2.1.303, 2026-10-14 to 2026-10-19, #991)

Read on 2026-10-19 from every Claude Code session file under `~/.claude/projects` whose folder is a kelpie worktree of any project and whose first line is on or after 2026-10-14: 89 worker sessions and 201 reviewer sessions, and one `adapters::mcp::live` probe. A session is a worker's when its prompt is the project's implementer's, and a reviewer's when it is kelpie's reviewer prompt. Session totals are the only deployment counts kept here: the tool calls and requests each session made stay out.

- No worker or reviewer session has a `mcp__codebase-memory-mcp__*` tool call, on any date. The only graph tool call among them is the probe's `list_projects`.
- `given the server` was read two ways. The `deferred_tools_delta` attachment's `failedMcpServers` naming `codebase-memory-mcp`: 13 worker and 29 reviewer sessions, all `CONNECTION_CLOSED`, all before #948. The session's `api-request-shape` line, which records the `tools` array Claude Code sends, holding the graph's 17 tools: 40 worker sessions (2026-10-18 to 10-19) and 88 reviewer sessions (2026-10-16 to 10-19), each also writing an `mcp_instructions_delta` line naming the server. A session given a server that never connects writes neither line.
- Those 17 definitions are 16,470 bytes of JSON as 2.1.302 and 2.1.303 send them, out of 28,926 bytes of tools for a worker's request and 22,660 for a reviewer's: 57% of what a worker sends, and the array is the same on every request of the call. At the 4,300 tokens measured above for the same 17 tools as 17,122 characters, that is about 4,100 tokens on every request of a call given the graph.
- The triage of #991 read the same transcripts before this and counted 51 worker sessions, 10 of them given the server, and 20 reviewer sessions with the tools. Its window is not recorded, and it is narrower than the read above.
