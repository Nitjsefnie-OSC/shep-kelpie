# Fence reads

What each role's call may read, and how those folders are granted. The write fence,
the guard and the hooks are in fence.md, and the measured facts behind these are in
`docs/facts/worker-profile-and-sandbox.md`.

- Every role's sandbox denies the machine's home folder whole and allows back what the work needs. `WorkerProfile` names `home`, and `reach` denies the outermost of the three homes (`profile::home_denials`), then carves back the worktree, the build folder, kelpie's binary, the git common dir, the cargo and rustup homes whole (a tool cannot exec under a deny of its own folder), `~/.gitconfig` and `~/.config/gh` on the maintainer's login, its plugin skill copies, and #952's sources. A credential named beside them stays denied by name, and each cargo home the fence reads back whole names its own `credentials` and `credentials.toml`, wherever `CARGO_HOME` moved that home (`dep_sources::cargo_credentials`). A call with no fence (a reviewer, a retro) and the pm's and `issues`' writer fences deny it the same way. A call with no fence takes its carve-backs at the harness rather than the profile: `harness::unfenced_reads` allows back its own folder, the git common dir its `git` runs through (a linked worktree's `.git` file names a gitdir outside the worktree), the cargo and rustup homes under each denied home, and its `~/.gitconfig`. Every one of them carves kelpie's own binary back as well: a hook runs it inside the fence (the pm's `confine --append` on its notes), and exec needs file-read of the file it runs. #1259, `crates/core/src/profile/mod.rs`
- Every call reads the installed sources and docs of its dependencies and toolchains: cargo's `registry/src` and `git/checkouts`, and each rustup toolchain's `lib/rustlib/src` and `share/doc`, each folder from the tool's own variable or its default home. A folder not on the machine adds nothing, and a variable that names a folder relative to wherever the tool was run names nothing, since each call runs its tool from a folder of its own. They are found as they are granted, not once when the runner starts: a machine gains a toolchain and a project gains its first git dependency while the runner runs, and a call rendered before that was granted neither. `Runner::prepared` puts them in the call's read list and the fence's read carve-outs, and a call built without it (a triager, a contribution's security reviewer and its pass reviewers) is granted the machine's own, having no build folder of its own: a contribution is named by its pull request, so `paths.build` of it would be another work item's folder. Claude Code's `additionalDirectories` and the sandbox's `allowRead` both let them through; the write list is untouched, and `CREDENTIALS` still denies what sits beside them. A call that works an item also gets the crates and the standard library of the `CARGO_HOME` and `RUSTUP_HOME` its `build_env` points into the build folder, and kelpie makes each of those folders as it grants it, since a harness judges its grants when the call starts and the call's own tool is what fills them. A build-local rustup home with no toolchain installed is granted as its whole `toolchains` folder, since no toolchain name is known until the call installs one. An answer and a researcher read none of them. #952, `crates/core/src/dep_sources.rs`, `runner/turn/dep_reads.rs`
- Each harness names what it reads to run, since the home deny would otherwise refuse the harness's own program (`harness::program_folder`), which names the program, what a link of it runs, the folder each runs from and the install folder above a `bin`, and for a bare name such as the default `claude` the `PATH` folder that holds it, read through the `Env` port so a test can name one. A script also names what its shebang runs, since the kernel execs that: `pi` is Node, and a version manager keeps `node` under the home. No grant opens the denied home whole, since a folder holding the harness's own home is the home itself or above it. Claude Code reads `~/.claude` and `~/.claude.json`, with `~/.claude/projects/**` denied and its own transcript folder allowed back. Its `Read` denies carve around the fence's read carve-outs and the call's read list, so a granted folder is not denied by the home rule. #1259, `crates/adapters/src/adapters/harness/policy.rs`
- A worker reads the project's skills folder, where kelpie writes every plugin of the call: a skill names a file under its plugin's folder (`${CLAUDE_PLUGIN_ROOT}/docs/rules.md`, `plugins.md`), and it reaches nothing while kelpie's home is unreadable whole. No other role is given it. #1258, `crates/core/src/profile/mod.rs`
