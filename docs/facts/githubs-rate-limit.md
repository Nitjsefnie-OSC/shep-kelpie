# GitHub's rate limit

- gh says a used-up GraphQL limit as `GraphQL: API rate limit already exceeded for user ID <n>.`, read from the live runner's log on 2026-10-10, where every board read failed that way for as long as the limit stayed used up.
- `gh api rate_limit` answers `{"resources": {"core": {...}, "graphql": {...}, ...}, "rate": {...}}`, each limit with `limit`, `used`, `remaining` and `reset` in seconds since the epoch; recorded 2026-10-10 as `fixtures/gh-api-rate-limit.json`. GitHub documents the endpoint as counting against no limit. The REST and secondary-limit texts kelpie also matches (`API rate limit exceeded`, `secondary rate limit`) are GitHub's documented messages, not recorded here.
- During an upgrade on the maintainer's live project, a drain's 500ms poll of `drain` and `status` woke the runner's loop for a full pass each time, so the runner read GitHub about every two seconds instead of once a minute, and a merged item's failing cleanup was retried 408 times in 13 minutes (4454 times during the previous day's upgrade). The account's 5,000-an-hour GraphQL limit ran out, and every runner on it failed its board reads until the reset.
- GitHub's documented secondary limits, from its REST docs and not recorded from a live answer: no more than 100 concurrent requests, no more than 900 points a minute for one REST endpoint, and no more than 80 content-generating requests a minute. A limited answer carries `retry-after` in seconds where GitHub gives one, and `x-ratelimit-reset` in seconds since the epoch for a primary limit. Kelpie caps a login at 60 calls a minute and 5 at once, well under all three.
- The headers kelpie reads from a `gh` call's stderr (`gh` run with `GH_DEBUG=api` prints the response headers) are an assumed format, not recorded: the sandbox's guard hook blocks `gh api`. The App's curl calls write the headers with `-w`, which is curl's own documented output.
- Conditional reads, measured 2026-10-13 with `curl` on a public repository's REST endpoints: an answer carries a weak `ETag`, and the same request with `If-None-Match: <etag>` comes back `304` with an empty body. The `ETag` varies with the request's `Accept` header, so a read has to send the same `Accept` every time, or the kept tag never matches: 4 of 4 repeated requests with one `Accept` came back `304`, and requests that differed in `Accept` did not. An unauthenticated `304` still cost one request of the 60-an-hour allowance, so the saving is documented for an authenticated request, which GitHub says does not count a `304`, and not measured here.
- `gh api` was not measured: the sandbox's guard hook blocks it, so whether it exits 0 or non-zero on a `304`, and what it prints, is unknown. GraphQL has no conditional requests, so the board listing, `gh pr view` and `gh issue view` cannot send `If-None-Match` at all.
- GraphQL prices a query by the connections it asks for, not by what comes back. Measured 2026-10-23 with `rateLimit(dryRun: true) { cost }`, which spent nothing, against a repo with 3 open pull requests: the board's listing cost 6 points, and 57 once it asked each commit's `checkSuites(first: 50)` for `checkRuns(first: 1) { totalCount }`, one request per suite of each of 100 pull requests. The suites without the count, and each rollup check run's `checkSuite { id }`, cost 7. At one listing a minute, two runners on the 57-point query spent the login's 5,000 an hour.
- The same hour, `gh api graphql` answered `{ rateLimit { remaining } }` with 4604 while its response's `x-ratelimit-remaining` header said 23 and every other query was refused, so the headers, not the `rateLimit` field, say whether a query will be answered.
- Over a 2 minute test (reported in #1195, not recorded here), the login's `core` `used` rose by 28 while the forge ledger held 30 REST calls, and its `graphql` `used` rose by 12 points for 39 GraphQL queries. So the ledger's REST count follows GitHub's, and GraphQL points are not queries. `used` returns to near zero at each `reset`.
